The 25-minute slot

Five stations, roughly 5 minutes each, with a short buffer for moving between them. The Construct taster has a visible on-screen countdown set to 6 minutes — the other four don't enforce a timer, so you'll need to call time yourself.

Construct ~5m
Vault ~5m
Ledger ~5m
Front ~5m
Helpdesk ~5m

Nobody needs to finish every task in every activity — the point is a real taste of each, not full completion. If someone's clearly engaged and close to finishing when time's up, let them carry on; don't cut mid-flow over a minute or two. Construct and Vault now have 5 tasks each rather than 3 — genuinely finishing either one in 5 minutes is a stretch goal, not an expectation.

The Construct

What it is: navigating a hidden rover across a grid by writing real JavaScript — moveForward(), turnLeft(), turnRight() — building from a single command up to a loop, and explicitly showing that a loop and manual repeated calls are equally valid solutions. Covers functions, sequencing, parameters, and loops.

#TaskAsks for
1Wake Upcall moveForward() once
2The Pathfour moveForward() calls in a row
3The Turnmove, turn, move again — combining direction changes
4The Relaytwo turns — three straight stretches chained together
5The Repeata diagonal staircase — solvable manually or with a loop, deliberately
BonusThe Glitchfix a loop that runs one time too few (debugging, not new syntax)

The Repeat is worth knowing about specifically: the path staircases diagonally rather than running in a straight line — deliberately, after feedback that a straight run didn't feel meaningfully harder than earlier tasks, just longer. The repeating unit is four commands (move, turn, move, turn back), not one, so the manual solution is genuinely long (16 lines) while the loop version stays at 4 — a much more dramatic and honest demonstration of why loops matter. The checking logic still only ever looks at where the rover ends up, never at what code got it there, so both the 16-line manual solution and the 4-line loop genuinely pass.

Scaffolded help

Tier 1 — ask, don't tell

"How many cells away is the exit? What do you think that number needs to be in your code?"

Tier 2 — point at the tool

Point them at the in-app Hint button before adding anything yourself — it escalates through three tiers on its own, ending in the full answer if they click it enough times.

Tier 3 — narrow it down

"You've got the right idea, but count your moveForward() calls again — you're one short." Still make them fix it themselves.

The Vault

What it is: writing real functions to patch broken business logic in a bank's risk-checking system, then running real test cases against them. Covers functions, return values, booleans, conditionals, and — new — a two-parameter conditional and a built-in maths function.

#FunctionAsks for
1calculateTotaladd a flat £5 fee to an amount
2isHighRiskreturn true/false for amounts over £10,000
3categoriseTransactionthree-way if/else banding
4applyLateFeetwo parameters, one used as a conditional gate
5roundToNearestPoundintroduces Math.round()
— take-home extension adds 3 more, see below —
6applyLoyaltyDiscountmultiple parameters, one a boolean flag
7calculateInteresttwo-parameter arithmetic
8flagSuspiciousActivitycompound condition with &&

Scaffolded help

Tier 1 — ask, don't tell

"What does the Test Console say your function actually returned? Is that different from what it expected?"

Tier 2 — the usual suspects

Missing return, or > vs >= not matching the brief exactly — ask them to re-read the brief's wording once more before anything else.

Tier 3 — narrow it down

Point at the specific failing test row and the exact value it returned vs expected — that's usually enough for someone to spot it themselves.

The Ledger

What it is: writing functions that loop through a real, visible list of transactions to answer questions — totals, filters, counts. Each function also gets tested against a second, hidden dataset, so hardcoding the visible numbers doesn't pass. Covers variables, arrays, objects, and loops.

If this was confusing before, it's had a real fix: the panel showing the data now explicitly spells out that row 1 (groceries, £120) is transactions[0].category and transactions[0].amount in code — that bridge was missing before and was very likely the actual cause of confusion, not the difficulty of the task itself. There was also a genuine layout bug where, on any narrow screen, the code editor rendered above the data table — fixed so the data always shows first.

Scaffolded help

Tier 1 — ask, don't tell

"Where's your total variable declared — inside the loop, or before it?" This catches the single most common bug here on its own.

Tier 2 — read it aloud

Get them to read their if condition out loud in plain English — mismatches between what they meant and what they typed usually surface immediately.

Tier 3 — narrow it down

If the visible-ledger test passes but the hidden one fails, that's a strong sign they hardcoded a number instead of writing real logic — worth saying so directly.

Answer key

totalSpend
function totalSpend(transactions) {
  let total = 0;
  for (let i = 0; i < transactions.length; i++) {
    total += transactions[i].amount;
  }
  return total;
}
sumByCategory
function sumByCategory(transactions, category) {
  let total = 0;
  for (let i = 0; i < transactions.length; i++) {
    if (transactions[i].category === category) {
      total += transactions[i].amount;
    }
  }
  return total;
}
countHighValue
function countHighValue(transactions, threshold) {
  let count = 0;
  for (let i = 0; i < transactions.length; i++) {
    if (transactions[i].amount > threshold) {
      count++;
    }
  }
  return count;
}
largestTransaction (extension)
function largestTransaction(transactions) {
  let biggest = 0;
  for (let i = 0; i < transactions.length; i++) {
    if (transactions[i].amount > biggest) {
      biggest = transactions[i].amount;
    }
  }
  return biggest;
}
averageTransaction (extension)
function averageTransaction(transactions) {
  let total = 0;
  for (let i = 0; i < transactions.length; i++) {
    total += transactions[i].amount;
  }
  return Math.round(total / transactions.length);
}
sumByCategories (extension)
function sumByCategories(transactions, categories) {
  let total = 0;
  for (let i = 0; i < transactions.length; i++) {
    if (categories.includes(transactions[i].category)) {
      total += transactions[i].amount;
    }
  }
  return total;
}

The Front

What it is: writing real CSS against a live preview to hit stated visual goals — checked by reading actual computed styles, not exact pixel matching. Covers selectors, the box model, typography, and flexbox.

Two real changes worth knowing about: there's now a colour picker next to the editor — click a swatch and it shows the hex code to copy, and the brief also says a plain colour name like navy works exactly as well as a hex code. Separately, the worked examples used to use values that would pass the actual checks if copied verbatim with just the selector renamed — that's fixed. The worked examples still show the right properties, but with deliberately small or slightly wrong values (e.g. justify-content: center instead of space-between), so a blind copy-paste no longer passes — genuine adaptation is required.

Each screen also has a collapsed "🌟 Try these extensions" box with two optional, unchecked stretch ideas — a hover effect, a box-shadow, a text-shadow, and so on. Nobody needs to do these to pass; they're there for anyone who finishes early. The take-home extension restructures the taster into one continuous page (header, nav, card, transaction list) instead of resetting between screens, with 2 extensions per section (8 total). Finishing all three now leads to a done screen with real options — ↺ Try Again resets everything, ⚡ Bonus Round starts a genuine CSS debugging challenge (see below) rather than a dead end.

The Helpdesk

What it is: a completely different mechanic from the other four — a live banking app is broken in five ways, and the participant plays with it, describes what's wrong to a support chat in their own words, and the chat summarises the problem, applies the fix directly to the code, and shows a diff of exactly what changed. No manual find-and-edit required. Two more "issues" are actually just polish suggestions, not bugs, to reward people who suggest improvements as well as spot faults.

There's no visible bug list. The old version showed a checklist naming all 5 known issues, which made the activity pointless — you could just read the list. Now there's only a progress bar showing how many have been found, never what they are. Discovery has to come from actually playing with the app.

The 5 real bugs

Deposit overwrites instead of adding

Symptom: depositing money resets the balance to the deposit amount instead of adding to it.

- balance = amt;
+ balance += amt;
Withdraw button does nothing

Symptom: clicking Withdraw has no effect at all. The button calls handleWithdraw(), but the function is defined as handelWithdraw() — a typo.

- function handelWithdraw(){
+ function handleWithdraw(){
Most recent transaction missing from the list

Symptom: the transaction history is always one entry short — the newest action never appears.

- for (let i = 0; i < transactions.length - 1; i++) {
+ for (let i = 0; i < transactions.length; i++) {
Transfers can push the balance negative

Symptom: entering a negative amount, or an amount larger than the balance, into Transfer goes through with no error.

- const amt = Number(document.getElementById('transferAmt').value);
-   balance -= amt;
+ const amt = Number(document.getElementById('transferAmt').value);
+   if (amt > 0 && amt <= balance) {
+     balance -= amt;
+   } else {
+     alert('Enter a valid amount');
+     return;
+   }
Balance displays a long, broken-looking number

Symptom: the balance sometimes shows something like 30.299999999999997 — genuine JavaScript floating-point behaviour, seeded deliberately into the starting balance so it's visible immediately on load, independent of the other four bugs.

- document.getElementById('balance').textContent = balance;
+ document.getElementById('balance').textContent = balance.toFixed(2);

The 2 "improvements" (not bugs — reward noticing these too)

Deposit box doesn't clear after use

Not broken, just rough — the amount stays in the input after a successful deposit.

  transactions.push('Deposited £' + amt);
+ document.getElementById('depositAmt').value = '';
Large balances are hard to read

Adds thousands separators. This one depends on the rounding bug being fixed first — the chat will say so if asked about it too early.

- document.getElementById('balance').textContent = balance.toFixed(2);
+ document.getElementById('balance').textContent = balance.toLocaleString(undefined, {minimumFractionDigits:2, maximumFractionDigits:2});

Help & Hints — what works and what doesn't

Construct, Vault, Ledger, and Front each used to have two separate support systems — a Hint button with its own box, and a completely separate chat with its own escalation logic that quietly duplicated what hints already gave. Feedback was blunt and correct: two places doing the same job is confusing, not more helpful. They're now genuinely one system.

How it works now

One destination, two doors in: clicking 💡 Hint (still in the main panel, same place as always) opens the chat panel and posts the hint there. Typing "I'm stuck" directly into the chat does the exact same thing — same counter, same progression, same gating. There's no second copy of the answer living anywhere else.
Gating still holds: after the first hint, the next tier is blocked with a clear amber message until a genuine Run attempt happens — whether that next hint was requested by clicking the button or by typing "I'm stuck" again.
General concept questions ("what's a function", "what does return do") are still answered directly and immediately in the same chat — these teach general syntax, not a specific answer, so there's no reason to hold them back or route them through hints.
Everyday word choices are understood too: "cash"/"money" instead of "amount", "spin" instead of "turn", "colour" either spelling, "tally" instead of "total" — a small synonym table normalizes these before matching.
What it still can't do: understand a genuinely novel phrasing that doesn't overlap with any known keyword, synonym, or stuck-phrase. That still gets the generic fallback — point them at 💡 Hint directly, or step in yourself.

Example exchange (Vault) — same hint state, two different doors in

clicks 💡 Hint→ chat opens, posts hint 1 (conceptual nudge)
clicks 💡 Hint again (no run yet)→ blocked: "try running your code first"
runs code, types "im really stuck"→ posts hint 2 — the SAME progression, triggered from chat instead of the button
"whats a function"→ answered directly, doesn't touch hint progress at all
Rebuilding this surfaced real bugs, not just a UI tidy-up: Vault Extended and both Construct files had never actually received the hint-gating fix from an earlier pass at all — hints could be spammed straight to the full answer with no gating, in those three files specifically, until this rebuild. Ledger's taster also had a second stale root@ledger:~$ terminal-prompt leftover, caught while going file by file. All fixed and re-verified; the bonus-round paths in Construct and Front (which resolve hints through a separate active-challenge reference rather than the normal array) were specifically tested through the merge rather than assumed to still work.
The earlier synonym-layer work still applies — a 22-query before/after comparison found 5 queries that used to hit the fallback now get a genuine answer, with zero regressions, and two coincidental false-matches it surfaced were fixed at the content level. That measurement and those fixes carried over unchanged into this rebuild.

Helpdesk chat — what works and what doesn't

This is a genuinely different system from the other four — it doesn't give hints, it applies real fixes automatically. Describing a problem gets you: a one-line summary of what's wrong, the fix applied directly into the code editor, and a red/green diff showing exactly what changed. The live app rebuilds and re-checks itself immediately after.

How it behaves

Recognised problems and improvements (7 total, see the answer key above): each has roughly 7-12 different phrasings it recognises — "the deposit doesn't add up right", "my balance just becomes whatever I deposit", "adding money isn't working" all correctly match the same deposit bug.
Fixes stack correctly: describing a second problem after the first applies its fix on top of the first, without undoing it — participants can work through issues in any order.
What it can't do — genuinely open-ended interpretation: despite feeling conversational, this is still keyword matching underneath, just with a much wider net and a much better payoff (an applied fix, not just text) than the other four chats. It cannot diagnose a problem it wasn't built to recognise.
"I can't find that exact spot right now": this appears in two real situations, both fine — either that line has already been changed (by chat or by hand), or (for the thousands-separator improvement specifically) an earlier fix hasn't landed yet. Tested and confirmed this fails gracefully rather than corrupting the code.
Manual editing still works alongside chat: participants can type directly into the code window instead of using chat at all — "Check My Fixes" runs the same checks either way. Worth mentioning this explicitly if someone wants to experiment by hand.

Example exchanges

"clicking withdraw does nothing at all"→ diagnoses the handelWithdraw typo, fixes it, shows diff
"large numbers are hard to read"→ works only after the rounding bug is already fixed; otherwise a graceful "can't find that" message
"what is the weather today"→ honest fallback, no fabricated fix

A separate "I'm stuck" path, for the harder-to-spot bugs

Feedback during testing was specific: for someone with no coding background, finding the last one or two bugs by clicking around is genuinely hard — the transfer-validation and missing-transaction bugs especially don't announce themselves the way a visibly broken button does. Rather than add them to a visible list (which would recreate the exact spoiler problem the redesign removed), there's now a second, separate detection path in the same chat.

How it works: phrases like "I'm stuck", "help", "what should I look for", or "I can't find any more bugs" are checked before the normal fix-matching — if recognised, the chat looks at which of the 5 real bugs haven't been found yet and nudges toward exploring one of them, without naming it. "Try transferring something unusual — a negative amount, or more than the balance actually has. What should happen, and what does?"
It tracks real progress, not a script: the nudge is generated from the same pass/fail state "Check My Fixes" already tracks — it will never point someone back at a bug they've already fixed, and once all 5 are genuinely found it says so plainly instead of repeating itself.
"im stuck" (nothing fixed yet)→ nudges toward the deposit bug specifically
"can't find any more bugs" (3 of 5 fixed)→ nudges toward one of the 2 remaining, never a fixed one
"help" (all 5 fixed)→ "you've actually found everything I know about"

Troubleshooting — user error, not the build

Every one of these has come up in testing and is a person doing something reasonable, not a bug in the files.

"I clicked Run and nothing happened."Check the Error box beneath the buttons — a syntax error (missing bracket, missing semicolon) stops the code from running at all, and the message is usually specific enough to spot the line. If the Error box is empty too, check they actually edited the function body — an empty // TODO with nothing added runs fine and just does nothing.
"My answer looks right but it's still failing."Almost always exact wording/case: "Groceries" won't match "groceries", and a typo'd function name means the test can't find the function at all — the error message will say so directly.
"The page looks completely unstyled / broken, no colours, no layout."These are self-contained single files with no other dependencies except a Google Fonts import — this is almost always a font failing to load over a blocked network. Check internet access on that machine.
"I can't type in the code box."Click directly inside the text area first — cursor focus can land on a button instead, especially on a trackpad. Not a bug, just needs a click.
"I hit Reset and lost my code."Working as intended — Reset wipes back to the starter code for that task, not just the visuals. Worth warning the room about this once up front rather than after someone loses a few minutes of work.
"The test console shows a weird value like NaN or undefined."NaN usually means a maths operation happened on something that wasn't a number (often a typo'd property name). undefined almost always means a missing return.
"Nothing in The Front changes when I edit the CSS."Check the selector actually matches — .account-card needs the dot; without it, it silently targets nothing.
"I copied the worked example exactly and it still failed."Working as intended, not a bug — Front's worked examples deliberately use values too small (or, for Layout, a different value entirely) to pass the real checks. Explain this is on purpose: the pattern is right, the numbers need adjusting.
Construct taster vs. full build — genuinely different levels 4 and 5, not just "full has one extra": both share Wake Up, The Path, and The Turn, but then diverge — the taster's own levels 4–5 are The Relay and The Repeat (documented above), while the full build has Agents and its own version of The Loop instead. The full build's Loop got the identical staircase redesign as the taster's Repeat, for the same reason (a straight line didn't feel meaningfully harder) — just slightly longer (5 diagonal cycles instead of 4), since it's untimed take-home work. Loop's answer is the same shape as Repeat's: a 4-line loop body of move/turn/move/turn-back, repeated, or the fully manual 20-line equivalent — both genuinely pass. The taster is a genuinely different file (mission-control-taster.html) with its own 6-minute timer. Don't hand out the full mission-control.html link during the live event by mistake — its timer now counts up with no deadline, which will look odd if someone's expecting a countdown.
